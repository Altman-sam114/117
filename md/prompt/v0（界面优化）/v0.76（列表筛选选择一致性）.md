## 2. 背景与问题

当前 `EntryListView` 自己持有搜索文本和分类筛选状态，并在 `body` 内构造 `JournalEntryListSnapshot`。`ContentView` 的 `selectedEntryID`、`repairSelection(with:)` 和 detail binding 只检查完整 `store.entries`；`journalEntryNavigationActions` 也把完整 `store.entries` 传给 `JournalEntryNavigation`。因此筛选后可能出现：

- selection 仍指向被搜索/分类筛掉的日记，detail 继续显示隐藏内容，或 List 的可见行与 selection 不一致。
- 筛选后删除、新建或 Store entries 变化时，selection 修复到完整 Store 数组首项，而不是当前可见结果首项。
- Mac Catalyst 较新/较早导航从当前筛选结果跳到隐藏日记。
- 列表和 focused scene navigation 使用不同筛选状态，无法共享同一可见顺序。

`JournalEntryListSnapshot` 已提供 `filteredEntries`，保留输入数组顺序；`JournalEntryNavigation.destinationID` 已按传入数组顺序、非循环地解析相邻日记。本轮主要修正生产接线和 selection policy，不改变这两个纯规则的既有语义。

## 3. 目标与验收语义

必须让当前筛选结果成为 selection、detail 和桌面导航的唯一有效集合：

1. 搜索或分类筛选后，selection 始终来自当前 `JournalEntryListSnapshot.filteredEntries`。当前 selection 仍可见时保留；当前 selection 被隐藏时切到可见 `filteredEntries.first?.id`；可见结果为空时为 `nil`。
2. 列表 selection、ContentView detail binding 的有效性、repair、创建/删除后的修复和 focused navigation 必须使用同一份当前筛选 snapshot，或完全等价的 `filteredEntries`；不能读取未筛选 `store.entries` 决定这些行为。
3. 删除日记后按当前筛选修复 selection。删除确认继续持有完整目标并沿现有 `ContentView -> JournalStore.delete(_:)` 链路执行。
4. 新建日记后按当前筛选修复 selection：新日记匹配筛选时可选择新 ID；新日记被搜索/分类隐藏时选择当前可见首项；当前筛选无结果时为 `nil`。不得留下隐藏的新建日记为 selection。
5. `store.entries` 因创建、删除、标题/正文/分类/心情/日期编辑或其他现有 mutation 变化时，均按新的当前筛选 snapshot 修复；可见 selection 保持，隐藏 selection 切首项，空结果为 nil。
6. Mac Catalyst 较新/较早日记只在当前筛选结果内导航，严格沿 `filteredEntries` 当前新到旧顺序；首尾继续独立禁用、不循环。动作只改变 selection，不调用 Store、不保存、不改变正文焦点。
7. 保留搜索 trim、标题/正文/分类/心情匹配、基于完整 entries 的分类计数、真实空集合与筛选空结果区分。

## 4. 推荐最小架构

推荐把 `searchText`、`selectedCategory` 和由 `store.entries` 派生的 `JournalEntryListSnapshot` 提升到 `ContentView`：

- `ContentView` 持有筛选状态并向 `EntryListView` 传入当前 snapshot 及搜索/分类 binding；`EntryListView` 只渲染和更新父级筛选状态，不再有分离的筛选 State 或另算 selection 来源。
- `ContentView.journalEntryNavigationActions` 使用同一个当前 snapshot 的 `filteredEntries` 调用 `JournalEntryNavigation.destinationID`。
- `selectInitialEntry`、筛选变化、`store.entries` 变化、`createEntry`、`deleteEntry` 和 detail guard 统一使用同一纯 selection policy。

可采用等价的最小架构，但必须保证列表、detail 和 focused navigation 消费同一筛选语义，不能在两个 View 中复制条件来掩盖状态分裂。建议在已有 utility 中增加 internal 纯值 `JournalEntrySelectionPolicy`，避免无必要新增工程文件；可放在 `JournalEntryListSnapshot.swift` 或 `JournalEntryNavigation.swift`，或使用等价位置。

策略语义必须等价于：current ID 在 visible entries 中则原样返回，否则返回 visible entries 的首个 ID；visible entries 为空则无条件返回 nil。生产修复路径和 XCTest 必须消费同一策略，不能测试专用复制 if/else。

## 5. 实现步骤与边界

1. 在 `ContentView` 集中持有搜索/分类状态和当前 `JournalEntryListSnapshot`，把 binding 与 snapshot 传给 `EntryListView`；列表行 tag 只能来自 `snapshot.filteredEntries`。
2. 在筛选状态变化后按最新 snapshot repair。必要时让 `selectedEntryBinding` 再以当前 visible entries 做 guard，防止隐藏 entry 进入 editor detail。
3. Store entries 发布变化后用新 entries 加当前筛选状态重建 snapshot，再 repair。创建先调用既有 `store.createEntry()`，再以新 snapshot 通过 policy 修复；删除仍只调用 `store.delete(_:)`，之后以删除后的 snapshot 修复。
4. `journalEntryNavigationActions` 只使用当前 snapshot 的 `filteredEntries`。保留 `JournalEntryNavigation` 既有方向、输入顺序、不排序、首尾不循环和快捷键元数据。
5. 保留 `EntryListView` 的搜索控件、分类 chip、完整 entries category counts、过滤空状态、统计入口、删除确认标题和单次消费语义。
6. 用 diff 证明 selection/filter 只是 UI 内存状态；不把筛选或 selection 放入 Store/JSON，不触发 revision、保存、Markdown 解析或正文 binding。

本轮不修改 `JournalStore`、`JournalEntry` JSON schema/兼容解码、Markdown parser/preview/`###` 语义、编辑器正文输入、统计算法、保存 debounce/flush/writer/错误仲裁、deployment target、第三方依赖、服务器、账号、数据库或独立 native macOS target。除必要的最小接线外，不修改无关 UI。

不得新建候选分支、PR 或 merge，不 force push；不得用 `AnyView`、全局可变筛选状态、固定等待、轮询、GCD、semaphore 或测试专用 policy。不要为了本轮改动现有删除后的邻居语义；本轮明确是隐藏切当前可见首项。

## 7. 纯 selection policy 测试

必须新增或扩展纯值 XCTest，测试生产实际消费的 policy，至少覆盖：

1. 可见保留：current selection 在 filteredEntries 中，repair 返回原 ID。
2. 隐藏切首项：current selection 不在 filteredEntries 中，repair 返回 filteredEntries 首项，而不是完整 Store 首项或隐藏项。
3. 空结果 nil：filteredEntries 为空时，无论 current selection 是 nil、可见候选或隐藏 ID，repair 均返回 nil。
4. 筛选删除：在 active search/category filter 下删除当前 selection，使用删除后的 filtered snapshot repair 到剩余可见首项；完整 Store 里仍存在但被隐藏的项不能被选回；无剩余可见项时为 nil。
5. 新建日记：覆盖新建日记匹配当前筛选时选择新 ID，以及新建日记不匹配时不留下隐藏 selection，而是当前可见首项或空结果 nil；至少一个断言使用新建后重新派生的 `JournalEntryListSnapshot`。
6. filtered navigation：将 `JournalEntryListSnapshot.filteredEntries` 传给 `JournalEntryNavigation`，确认较新/较早只在可见顺序相邻项间移动，隐藏项不是目标，首尾不循环。

可保留并扩展已有搜索、分类计数、空状态、删除确认和导航测试。禁止 SwiftUI host、真实菜单、系统 confirmation dialog、鼠标/触控板/键盘事件、模拟器、截图或 snapshot test。纯 policy 测试不能伪造真实 UI 验收；真实 List selection 时序、detail 瞬态、菜单 disabled 视觉、焦点、VoiceOver、Dynamic Type 和输入设备仍需人工说明为风险。

当前 v0.75 云端 XCTest 基线为 `189 passed`；本轮新增测试后总数必须高于 189，新增测试须按名称各执行一次并通过，最终以最新 artifact 的 `xctest.log` 或 `MDJournalTests.xcresult` 为准。JUnit 的固定四阶段摘要不可替代 XCTest 总数。

- 无法在不修改 JournalStore、JSON、Markdown、正文 binding 或保存语义的前提下让生产 selection/navigation 使用 filteredEntries。
