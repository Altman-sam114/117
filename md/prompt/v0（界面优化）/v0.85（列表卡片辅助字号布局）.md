## 背景与 EntryRow 证据

当前列表卡片在普通字号下可读，但 Accessibility Dynamic Type 下有明确布局缺口：

1. `MDJournal/Views/EntryRowView.swift:11-31` 顶部 metadata 使用固定横向 `HStack`，分类、心情图标和日期共用一行；较大辅助字号或窄 Mac Catalyst sidebar 下容易挤压。
2. `EntryRowView.swift:33-36` 标题固定 `.lineLimit(1)`，长标题在辅助字号下会被截断，用户无法完整辨认日记。
3. `EntryRowView.swift:46-55` footer 将词数、小节数、更新时间固定放在横向 `HStack`，并用 `.lineLimit(1)` 强制单行；较大字号下信息可能被压缩或截断。
4. `EntryRowView.swift:69-97` 小节条始终使用水平 `ScrollView` + `HStack`，每个小节标题在 `EntryRowView.swift:80-87` 固定 `.lineLimit(1)`。仅把行数改成 2 不足以解决问题：水平 ScrollView/HStack 可能给子 Text 无限或过宽的水平提议，文本仍不换行，卡片会横向增长或依赖不可发现的滚动。
5. `MDJournal/Views/EntryListView.swift:54-65` 通过 `ForEach(snapshot.filteredEntries)` 直接承载 EntryRow；列表 selection、删除手势、context menu 和当前 `JournalEntryListSnapshot` 都不应因本轮布局改动而改变。
6. 当前没有 `EntryRowLayoutContract`。编辑器已有 `MDJournal/Views/EntryEditorView.swift:12-41` 的 Dynamic Type 契约，但它只约束编辑器头部，不能替代列表卡片契约。

v0.84 已让 `JournalEntryBodySummary` 在模型层共享一次正文扫描；本轮应继续让 EntryRow 只消费一次 `entry.bodySummary`，不得把正文派生重新散落到视图层。

## 本轮目标

1. 为 `EntryRowView` 增加最小、纯值、非持久化的 `EntryRowLayoutContract`，由 `DynamicTypeSize` 决定普通字号和 Accessibility 字号的布局策略。
2. 普通 Dynamic Type（至少 `.large`、`.xxxLarge`）保持现有卡片的横向 metadata、横向 footer、标题单行和水平小节条行为，避免视觉回归。
3. Accessibility Dynamic Type（`.accessibility1` 至 `.accessibility5`）让 metadata 垂直堆叠，footer 使用垂直可读布局，标题取消单行截断，小节标题至少允许两行并在有限宽度内真实换行。
4. 保留分类、心情、日期、摘要、词数、小节数、更新时间、小节标题和 `+N` 的当前信息语义；只调整它们在辅助字号下的排列和可见行数。
5. 让窄 sidebar、iPhone 窄屏和 Mac Catalyst 列表在大字号下自然增高，不依赖横向无限增长，不改变 selection 或 `JournalStore` 数据链路。

## EntryRowLayoutContract 设计

建议新增一个与 `EntryEditorLayoutContract` 同样纯值、可 `Equatable` 断言的内部契约。字段名可按现有代码风格调整，但语义必须清晰且可由测试直接断言：

- `metadataAxis`：普通字号为 `.horizontal`，Accessibility 字号为 `.vertical`。
- `footerAxis`：普通字号为 `.horizontal`，Accessibility 字号为 `.vertical`；Accessibility 路径不得再依赖 HStack 的“自动换行”假设，因为 HStack 本身不会换行。
- `titleLineLimit`：普通字号为 `1`，Accessibility 字号为 `nil`，让长标题在有限卡片宽度内自然增高。
- `sectionTitleLineLimit`：普通字号为 `1`，Accessibility 至少为 `2`。若使用 `nil`，必须仍能证明文本在有限宽度内换行，不得只在无限水平提议中取消限制。
- `usesVerticalSectionLayout` 或等价字段：普通字号为 `false`，Accessibility 为 `true`。该字段用于避免 Accessibility 分支继续使用水平 `ScrollView`/`HStack` 的无限水平提议。
- 如需明确稳定尺寸，可为 Accessibility section label 定义正有限的最小/最大约束；不要定义会随内容无限增长的固定宽度。不要将卡片整体固定高度。

契约初始化应以 `dynamicTypeSize.isAccessibilitySize` 为唯一大字号分支依据。`.large`、`.xxxLarge` 等普通字号保留现有策略；不要按屏幕宽度、entry 内容长度或当前 selection 改变契约，以免把数据状态和布局策略耦合。

## Dynamic Type 布局语义

### Metadata

- 普通字号保持当前 `HStack(spacing: 8)`：分类 label、心情 icon-only label、Spacer、日期仍按当前视觉顺序排列。
- Accessibility 字号改为 leading-aligned `VStack` 或等价的垂直布局，分类、心情和日期各自得到有限且可读的行空间；日期不再被 Spacer 挤到同一行末端。
- 保留现有分类 tint、心情 system image、日期格式、padding、颜色和既有 accessibility label 语义；不要为了布局改写模型枚举或日期 formatter。
- 不能通过缩小 `.caption`、截断分类/日期或隐藏心情来解决挤压。

### Title

- 普通字号继续 `.lineLimit(1)`，维持列表密度。
- Accessibility 字号取消单行限制，允许标题在卡片可用宽度内自然换行并使卡片增高；不要使用 `minimumScaleFactor`、裁切或滚动标题。
- 标题的 `displayTitle` 来源和空标题 fallback 保持不变；布局契约只控制行数，不改文本。

### Summary

- 摘要继续消费 v0.84 的 `bodySummary.excerpt`，保留当前 `.lineLimit(2)` 与垂直可扩展语义，除非源码证明 Accessibility 下需要最小且局部的自然增高调整。
- 不为了实现 EntryRow Dynamic Type 再次调用 `entry.body`、`bodySummary` 或任何 summary/metrics 扫描。

### Footer

- 普通字号保持当前词数、分隔点、小节数、分隔点、更新时间的横向顺序和单行策略。
- Accessibility 字号使用 leading-aligned `VStack` 或等价的明确换行布局，保留三个信息项及其顺序；不要把三个项目放在仍不会换行的 HStack 中后仅移除 `.lineLimit(1)`。
- 可以在 Accessibility 分支移除单独占一行的 `·` 分隔点，或将分隔语义整合进可读行，但不得丢失词数、小节数或更新时间；普通字号不要改变现有分隔点视觉。
- 不改变相对更新时间生成逻辑，也不把 footer 信息写入模型或 JSON。

### Sections

- 普通字号继续使用当前水平 `ScrollView(.horizontal)`、前三个 section、`+N` 计数、单行小节标题和现有 chip 视觉，以保持列表密度与既有行为。
- Accessibility 字号必须使用不产生无限水平提议的垂直 section layout：例如 `VStack`/`LazyVStack` 中逐项放置前三个 section，再放置 `+N`；不要继续把可换行 Text 放在水平 ScrollView/HStack 中。
- Accessibility section title 必须在卡片有限宽度内至少允许两行；必要时在 title Text 上使用 `frame(maxWidth: .infinity, alignment: .leading)` 或等价有限宽度约束，再应用 padding/background，确保 `lineLimit(2)` 实际有机会换行。
- Accessibility section chip 可以自然增高，不能固定卡片整体高度、压缩字体或依赖用户发现横向滚动。只展示前三个 section 的现有数据范围不得改变。
- 空 sections 的“未添加 ### 小节”状态也必须在 Accessibility 分支可读；不要在水平滚动容器中留下一个无限提议的空状态。
- `+N` 必须保留并在可见 section 列表后以稳定顺序展示；不能因为切换垂直布局而误删计数或改变 `sectionCount`。

## 避免水平滚动无限提议陷阱

- SwiftUI `HStack` 不会自动换行；移除 `.lineLimit(1)` 并不能让 HStack 产生多行。
- 水平 `ScrollView` 的内容通常获得不受限的水平提议；其中的 `Text` 可能保持单行并把 chip 撑宽，导致卡片横向增长，而不是在 sidebar 内换行。
- 因此 Accessibility section layout 必须在非水平滚动容器中构造，或明确设置一个来源于父卡片可用宽度且不会无限增长的宽度约束；优先使用垂直列表让卡片自然增高。
- 不要用 `GeometryReader` 读取不稳定的窗口宽度来建立跨状态缓存；本轮只需让 SwiftUI 父布局给 Text 有限提议。
- 不要把水平滚动保留为 Accessibility 的唯一兜底，也不要用 `fixedSize(horizontal: true, vertical: false)` 强化横向增长。
- 普通字号的水平 section strip 是既有密度策略，可以保留；本轮要求的是 Accessibility 分支的真实可读性，而不是删除所有现有横向滚动。

7. Agent C 必须核对 artifact 未加密、GitHub 声明 size 与本地 size、GitHub digest 与本地 SHA-256、`unzip -t` CRC、clean/fresh extract 文件清单和逐文件 SHA-256。manifest 身份不匹配或 artifact 不完整时不得宣称通过。

### 阶段二：docs-close HEAD

1. 阶段一通过后，Agent B/C 按真实结果更新 `README.md`、`md/test/test.md`、`md/flow/flow.md`、`md/flow/flowchart.md` 和 `update_log.md`；写入实现 commit、最终 docs HEAD、run、attempt、artifact 名称/ID、size、digest、测试数量和遗留风险，不填入猜测值。
2. docs-close 必须继续在 `main` 推送并触发新的 `MD Journal CI Results` run。文档-only commit 也会改变最新 HEAD，不能复用阶段一 artifact。
3. Agent C 必须重新下载阶段二最新 `origin/main` HEAD 的未加密 artifact，并重复 manifest/JUnit/log/xcresult、digest、size、CRC、fresh extract、清单和逐文件 SHA-256 全部核对。
4. 只有阶段二 artifact 与最新 `origin/main` 完全一致，四阶段 outcome 全部通过，新增 contract 测试实际通过且文档真实完整时，v0.85 才能记录为完成。
5. 阶段一或阶段二失败时，不得回滚或拿旧 artifact 顶替；由 Agent B 在 `main` 追加最小修复 commit 后重新触发完整验收。

## 文档同步要求

实现阶段必须同步当前真实状态，不能用模板或预填 run：

- `README.md`：记录 EntryRow 在 Accessibility Dynamic Type 下的 metadata/footer/title/section 布局、普通字号兼容行为、云端结果和真实 UI 验收限制。
- `md/test/test.md`：记录 `EntryRowLayoutContract` 纯值矩阵测试、204 passed 基线、本机禁令、实际 XCTest 数量和两阶段 artifact 验收规则；说明 contract 不等价于真实像素/VoiceOver 测试。
- `md/flow/flow.md`：更新 EntryRow 的真实布局派生流，说明 layout contract 只消费 Dynamic Type，不进入 Store/JSON/selection；说明 Accessibility section 使用有限宽度垂直布局避免水平无限提议。
- `md/flow/flowchart.md`：补充 Dynamic Type -> `EntryRowLayoutContract` -> metadata/footer/title/section layout 的当前数据流，并记录真实 v0.85 两阶段云端结果。
- `update_log.md`：记录版本、日期、目标、关键文件、实现 HEAD、docs-close HEAD、run id、attempt、artifact、digest、测试数量、未运行项目和遗留风险。
- `.github/workflows/ci-results.yml`：仅将已有 `VERSION` 元数据更新为 `v0.85`，不扩大 workflow 行为。

## 风险与停止条件

- 最大 UI 风险是 Accessibility section 标题仍处于水平 ScrollView/HStack 的无限水平提议中，导致“lineLimit=2”不真正换行。若实现不能证明有限宽度垂直路径，应停止，不把静态行数字段当作完成。
- 另一个风险是 Accessibility footer 只移除 `.lineLimit(1)` 却保留 HStack；HStack 不会自动换行，必须改为明确的垂直或真正有限宽度布局。
- 普通字号若出现 metadata/footer/section 视觉行为变化、卡片密度变化或列表 selection/detail 回归，停止并退回最小修复。
- 纯 contract 测试、Swift parse、云端 build/XCTest 和 artifact 完整性不能证明真实 Mac Catalyst/iPhone Dynamic Type frame、List 行高、VoiceOver、触控板/鼠标或横向滚动体验；不得伪称这些已通过。
- 发现 JSON schema、Store、snapshot、focus、window、Markdown parser/preview 或摘要 metrics 无关 diff 时，停止并收窄范围。
- 如果无法同步 `origin/main`、工作区有无法判断归属的冲突、GitHub Actions 权限/artifact 下载失败、manifest 身份不匹配，立即记录具体阻塞并暂停。
- 同一 CI 原因连续失败 3 轮、连续 2 轮没有有效 diff、需要账号/密钥/付费服务/人工选择，或总目标要求改变时，停止循环并等待人工决定。
- 禁止删除、覆盖或批量改写用户日记；禁止把旧 run、旧 artifact、本地输出或未验证的预填值冒充 v0.85 结果。

## Agent X 下一步判断

- 阶段一 artifact 通过且源码 diff、纯 contract 测试和范围边界正确：进入 docs-close 阶段。
- 阶段一或阶段二 artifact 失败但原因可由最小范围修复：退回 Agent B 在 `main` 追加修复后重新触发完整验收，不做回滚式处理。
