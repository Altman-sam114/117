## 背景与当前行为证据

当前删除链路为：

```text
EntryListView.contextMenu / swipeActions
  -> 立即 onDelete(entry)
  -> ContentView.deleteEntry(_)
  -> JournalStore.delete(_)
  -> removeAll + saveImmediately
  -> ContentView.repairSelection
```

具体边界：

- `EntryListView` 的 `contextMenu` 和 `swipeActions` 各自直接调用 `onDelete(entry)`，没有共享请求状态，也没有系统确认界面。
- `ContentView.deleteEntry(_:)` 是现有删除回调实现，调用 `store.delete(entry)` 后执行既有 selection repair。
- `JournalStore.delete(_:)` 是唯一集合删除和本地 JSON 持久化入口，删除后立即保存。
- 列表可能同时处于搜索和分类筛选状态；确认期间目标可能已经不在当前 `filteredEntries` 中，因此不能只保存 ID 后再从筛选结果查回目标。
- 本轮必须在 `EntryListView` 的交互层增加确认保护，不得把确认职责下沉到 Store，也不得复制删除或 selection repair 逻辑。

## 本轮目标

1. 为右键菜单 `contextMenu` 和滑动操作 `swipeActions` 的“删除日记”动作增加统一的系统 `confirmationDialog`。

## 架构依据与状态设计

### 1. 责任边界

- `EntryListView` 拥有删除触发 UI，因此待确认状态和 `confirmationDialog` 应留在列表交互层。
- `ContentView` 继续只负责把确认后的 `JournalEntry` 交给 Store，并执行 selection repair。
- `JournalStore` 继续作为唯一集合删除与本地持久化入口；不得在 View 中直接改写 entries 或 JSON。

### 2. internal 纯状态契约或 reducer

在 `EntryListView.swift` 中定义一个 internal 类型，名称可按现有风格选择，例如 `JournalDeletionConfirmationState`。不要设为 `private`，否则 `@testable import MDJournal` 无法测试；也不要设为 `public` 扩大 API。

状态契约至少应具备等价能力：

```swift
struct JournalDeletionConfirmationState {
    private(set) var target: JournalEntry?

    var isPresented: Bool { target != nil }

    mutating func request(_ entry: JournalEntry)
    mutating func dismiss()
    mutating func consumeConfirmedTarget() -> JournalEntry?

    static func dialogTitle(for entry: JournalEntry) -> String
}
```

允许采用语义等价的 reducer/event 设计，但必须满足：

- `request(_:)` 保存完整值目标；不得只保存 ID。
- 新请求可以明确替换旧待确认目标，最终标题和确认结果都对应最后一次请求。
- `dismiss()` 幂等清空目标。
- `consumeConfirmedTarget()` 在返回目标前先清空内部状态；第一次确认返回准确目标，之后重复调用返回 `nil`。
- 状态类型不持有 Store、Binding、View、筛选快照或 closure，不产生 I/O，不直接删除。
- 对话框标题函数使用所持目标的 `displayTitle`，保证空标题日记也得到当前应用一致的可见标题；不得从 selection 或列表重新查找。

如果 `confirmationDialog` 的 `isPresented` 需要 `Binding<Bool>`，setter 收到 `false` 时必须调用状态的 `dismiss()`。不要让系统外部 dismiss 后残留 target。确认按钮闭包应调用 `consumeConfirmedTarget()`，仅在返回非 nil 时执行 `onDelete`。

### 3. 单一 UI 请求路径

两个入口应调用同一个小方法，例如：

```swift
private func requestDeletion(of entry: JournalEntry) {
    deletionConfirmation.request(entry)
}
```

要求：

- `contextMenu` 的 destructive Button 只调用 `requestDeletion(of: entry)`。
- `swipeActions` 的 destructive Button 只调用 `requestDeletion(of: entry)`。
- 两个入口均不得出现 `onDelete(entry)`。
- 只挂载一个共享 `confirmationDialog`，避免每一行重复维护 presentation 状态或出现多个对话框竞争。
- 对话框必须使用 SwiftUI 系统 API，并位于包含这两个触发入口的合理视图层级；不得用 `onTapGesture`、自定义 overlay 或手写弹窗。

### 4. 确认、取消和外部关闭

对话框语义必须包含：

- 标题：准确包含稳定目标的 `displayTitle`，建议 `删除“\(target.displayTitle)”？`。
- destructive 按钮：`Button("删除", role: .destructive)`。
- cancel 按钮：`Button("取消", role: .cancel)`。
- message：明确操作无法撤销。

行为顺序：

```text
confirm
  -> consumeConfirmedTarget() 先清空并返回目标
  -> guard 有目标
  -> 调用一次既有 onDelete(target)

cancel / Esc / 点击外部 / system dismiss
  -> dismiss()
  -> 不调用 onDelete
```

不得依赖“SwiftUI 通常会自动清状态”的隐含行为；生产接线必须显式覆盖 cancel 和 `isPresented = false`。也不得在 `onDelete` 返回后才清状态，因为同步状态刷新或重入可能导致重复确认。

## 自动化测试要求

在 `JournalEntryListSnapshotTests.swift` 新增 4 项纯 XCTest，名称可按项目风格调整，但必须覆盖以下行为，而非仅检查源码字符串：

1. **请求稳定持有完整目标并生成准确标题**
   - 创建具有固定 UUID、明确 title、body、日期、分类和心情的 `JournalEntry`。
   - `request(entry)` 后断言 `isPresented == true`。
   - 断言 target 的 ID、标题和至少一个非 ID 字段仍与请求值一致，证明不是仅 ID 状态。
   - 断言 dialog title 精确包含该目标的 `displayTitle`，且不会使用其他 selection 或列表项标题。

2. **取消和外部 dismiss 清理且不产生确认目标**
   - request 后调用 dismiss，断言 target 为 nil、`isPresented == false`。
   - dismiss 后调用 consume，必须返回 nil。
   - 再次 dismiss 仍保持空状态，证明幂等。

3. **确认只消费一次准确目标**
   - request 后第一次 consume 返回准确的原目标，同时状态已经清空。
   - 第二次 consume 返回 nil，锁定重复确认不得重复删除。
   - 测试名称与断言应明确表达“consume once”，不能只断言 target 最终为空。

4. **新请求替换旧请求且不依赖筛选结果回查**
   - 依次 request 两篇不同日记，断言标题和 consume 结果只对应最后一次请求。
   - 测试中的源数组可被清空或改为不包含目标，状态仍应返回已持有的目标值；状态 API 不接受 filteredEntries 或 selection 作为确认输入。
