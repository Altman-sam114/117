# v0.67（正文输入直接写回）

## 版本分配依据

- 当前最新已闭环正式版本为 `v0.66`。本轮继续服务 Agent X 总目标中的高效写入和 Mac Catalyst 长文写作性能，针对正文 UIKit bridge 的每次真实输入移除一段可证明冗余的读取与比较，因此沿 `v0.x` 小版本递增为 `v0.67`。
- 本轮不改变用户可见功能、Markdown 语法、存储格式或平台范围，只优化现有输入状态流并补充确定性回归测试，不开新大版本。

## 背景

`MarkdownBodyTextView.Coordinator` 当前把普通输入、Markdown 回车续写和行缩进结果同步到正文 `Binding<String>`。三条成功路径最终都调用 `updateTextIfNeeded(_:)`，该 helper 会先读取 `text.wrappedValue`，再与 UIKit 已经确认或规则层已经生成的新正文做整篇字符串比较，只有不同时才写 setter。

对于这些路径，变化已经由事件契约或纯规则返回值确认：

- `textViewDidChange(_:)` 表示 `UITextView` 正文已经发生变化；
- `MarkdownLineContinuation.apply(...)` 返回非 `nil` 时，bridge 已采用其新正文并阻止系统默认替换；
- `MarkdownLineIndentation.apply(...)` 返回非 `nil` 时，bridge 已采用其新正文和新选区。

因此，在 setter 之前再次读取旧正文没有判定价值。当前正文 binding 来自 `EntryEditorView` 的 `$entry.body`，其上游是 `ContentView.selectedEntryBinding`；这次显式旧值读取会穿透 binding getter，触发按 ID 查找当前 entry，并在长正文上比较公共前缀。真正的正文 setter、`JournalStore.update(_:)` 和保存节流仍然是必要状态流，本轮只移除提交前的冗余 getter 和全文相等判断，不宣称消除 setter 实现自身所需的所有上游工作。

v0.43 已建立正文、选区和焦点按需写回语义。本轮必须保留其核心结果：一次真实输入只发布一次正文；选区和焦点仍只在值改变时发布；外部 SwiftUI 状态同步到 UIKit 时仍先比较；程序化应用续写或缩进结果不能造成第二次正文发布。

## 本轮目标

- 将 `UITextViewDelegate` 已确认正文变化后的同步改为直接、且仅一次写入 `text.wrappedValue`，不先读取旧正文。
- Markdown 回车续写成功路径在应用 `result.body` 后直接、且仅一次写入正文 binding。
- Tab / Shift-Tab 或菜单/工具栏触发的行缩进成功路径在应用 `result.body` 后直接、且仅一次写入正文 binding。
- 保持 `updateUIView` 的外部正文同步差异检查，避免 SwiftUI 重绘时无条件覆盖 `UITextView.text`。
- 保持 marked text / IME 守卫、UTF-16 选区、焦点调度、输入 traits、字体配置及 v0.43 的选区/焦点去重语义。
- 增加确定性的 getter/setter 计数测试，直接证明三条成功输入路径对正文 binding 执行 `0` 次 getter、`1` 次 setter，并核对正文和选区结果。
- 更新 workflow 结果包版本为 `v0.67`，同步受影响文档，并完成 `main -> origin/main -> GitHub Actions artifact -> Agent C` 验收闭环。

## 非目标

- 不修改 `ContentView.selectedEntryBinding`、`JournalStore.entry(with:)`、`JournalStore.update(_:)`、保存 debounce、排序、JSON 编解码或本地文件格式。
- 不重构 `Binding<JournalEntry>` 或引入新的 store 写入 API；本轮只删除 bridge 提交前的冗余正文 getter。
- 不修改 `MarkdownLineContinuation`、`MarkdownLineIndentation` 的字符串规则、返回值或边界语义。
- 不改变回车默认输入、列表/待办/引用/有序列表续写、空项退出、fenced code、Tab / Shift-Tab 或菜单/工具栏缩进的用户行为。
- 不改变 `makeUIView`、`updateUIView` 的外部状态同步职责，不取消外部正文差异比较。
- 不改变正文选区、焦点、placeholder、编辑/预览布局、Mac 专注写作布局或任何 UI 视觉样式。
- 不引入性能耗时阈值、内存分配阈值、随机测试、第三方依赖、新 target 或新 deployment target。

## 架构与状态流

### 架构依据

- `MarkdownBodyTextView` 是 UIKit/SwiftUI 正文 bridge，负责接收 UIKit 输入事件并把正文、选区和焦点同步到 SwiftUI binding。
- `MarkdownLineContinuation` 与 `MarkdownLineIndentation` 是纯规则层；它们负责判断是否产生变换并返回完整结果，bridge 只应用结果，不复制规则。
- `EntryEditorView` 继续把 `$entry.body`、`bodySelectedRange` 和 `editorFocused` 传给 bridge。
- `ContentView.selectedEntryBinding` 继续把 entry 更新交给 `JournalStore.update(_:)`；`JournalStore` 仍是唯一集合修改和持久化入口。
- `updateUIView` 属于 SwiftUI 到 UIKit 的外部同步路径。它无法假设外部值一定变化，必须保留 `textView.text != text` 比较和 marked text 守卫。
- delegate 的普通正文变化、成功续写和成功缩进属于 UIKit 到 SwiftUI 的已确认提交路径。它们不需要通过旧正文 getter 再确认变化。

### 目标状态流

普通输入：

```text
UITextView 已完成系统输入
-> textViewDidChange
-> 直接写 text.wrappedValue 一次
-> 按需同步 selectedRange
-> EntryEditorView.entry.body
-> ContentView.selectedEntryBinding setter
-> JournalStore.update
```

Markdown 回车续写：

```text
shouldChangeTextIn（无 marked text）
-> MarkdownLineContinuation.apply 返回 Result
-> 设置 textView.text 和 textView.selectedRange
-> 直接写 result.body 一次
-> 按需同步 result.selectedRange
-> return false，阻止系统再次应用 replacement
```

行缩进：

```text
Tab / Shift-Tab / 既有缩进入口
-> applyIndentation（无 marked text）
-> MarkdownLineIndentation.apply 返回 Result
-> 设置 textView.text 和 textView.selectedRange
-> 直接写 result.body 一次
-> 按需同步 result.selectedRange
```

外部状态同步：

```text
SwiftUI 更新 MarkdownBodyTextView
-> updateUIView
-> markedTextRange == nil 且 textView.text != text 时才设置 UIKit 正文
-> 按需修复选区和焦点
```

## 实现步骤

1. 开始前按 `AGENTS.md` 重新阅读入口文档和本提示词，执行同步检查：

   ```sh
   git fetch origin
   git switch main
   git pull --ff-only origin main
   git status --short --branch

   ```

   确认当前分支为 `main`、基线为最新 `origin/main`、工作区没有无法判断归属的改动。远端 URL 中的 token 不得写入文档或最终回复。若无法同步、没有 `origin` 或出现归属不明冲突，停止并记录阻塞。

2. 在 `MarkdownBodyTextView.Coordinator` 中把“直接发布已确认正文”的语义与“未知值按需比较”区分清楚：
   - 普通输入 `textViewDidChange(_:)` 直接设置正文 binding 一次；
   - 回车续写 `MarkdownLineContinuation.apply(...)` 成功后直接设置 `result.body` 一次；
   - `MarkdownLineIndentation.apply(...)` 成功后直接设置 `result.body` 一次；
   - 这三条路径不得调用正文 binding getter，不得执行 `text.wrappedValue != newText`，也不得新增 coordinator 缓存后再做另一轮整篇字符串比较；
   - 可将 helper 命名为 `publishText(_:)`、`commitText(_:)` 等能表达“调用者已确认变化”的名称，其实现只能写 setter，不读 getter；也可直接在三处赋值，但优先保持既有集中同步风格且避免重复代码。

3. 保持 v0.43 及现有 bridge 语义：
   - `updateSelectedRangeIfNeeded(_:)` 和 `updateFocusIfNeeded(_:)` 继续读取对应轻量 binding 值并只在不同时写入；
   - `shouldChangeTextIn` 和 `applyIndentation` 的 marked text 守卫不变；IME 组合输入仍走系统默认路径，`updateUIView` 在 marked text 存在时不得覆盖正文或选区；
   - `updateUIView` 继续比较 `textView.text` 与外部 `text` 后再同步，不得改成无条件赋值；
   - 回车续写和缩进继续先把完整结果应用到 `UITextView`，再发布正文和选区；成功续写继续 `return false`；无结果时保留原默认行为；
   - 不增加手动调用 `textViewDidChange`、通知模拟、异步补写或第二个 setter。

4. 在 `MarkdownTextInputConfigurationTests.swift` 增加最小 Binding probe：
   - probe 使用引用类型保存 `value`、`getterCount`、`setterCount`，并生成 `Binding<Value>`；
   - getter 每次读取递增 `getterCount`，setter 每次写入递增 `setterCount` 并保存新值；
   - 测试不得依赖 wall-clock、sleep、Instruments、输入法 UI、通知投递顺序或 SwiftUI 完整 view 生命周期。

5. 至少新增以下三个确定性 bridge 测试，直接实例化 `MarkdownBodyTextView.Coordinator` 并注入 probe binding：
   - 普通输入：设置 `UITextView.text` 和选区后直接调用 `textViewDidChange(_:)`，断言正文 probe `getterCount == 0`、`setterCount == 1`、最终值等于 text view 正文；同时确认选区仍同步到预期值。
   - Markdown 回车续写：准备一个会产生明确 `MarkdownLineContinuation.Result` 的正文和光标，通过 coordinator 的 `textView(_:shouldChangeTextIn:replacementText:)` 触发，断言返回 `false`、UITextView 正文/选区正确、正文 probe `getterCount == 0`、`setterCount == 1`。优先使用简单无序列表，规则细节仍由现有 `MarkdownLineContinuationTests` 全面覆盖。
   - 成功缩进：准备一个会产生明确 `MarkdownLineIndentation.Result` 的正文和选区，调用 coordinator 的 `applyIndentation`，断言 UITextView 正文/选区正确、正文 probe `getterCount == 0`、`setterCount == 1`。只需选一个稳定的 indent 场景；Tab/Shift-Tab 全规则继续由现有 `MarkdownLineIndentationTests` 覆盖。

6. 补充防重复和边界断言：
   - 三个测试都必须独立创建 probe 和 coordinator，避免计数互相污染；
   - 断言一次 delegate/规则成功调用只产生一个正文 setter，不能只断言最终字符串；
   - 如 helper 保持 internal，可直接由 `@testable import MDJournal` 访问 Coordinator；不要为了测试把 API 改成 public；
   - 不要求真实键盘事件、真实 first responder 或 marked text 对象的 UI 测试，因为这些需要运行 UIKit 交互环境且不适合本轮确定性单元测试。IME 安全由保留现有守卫、源码审查、iOS/Mac Catalyst build 和现有输入链路回归共同验证，最终仍应在遗留风险中注明未做真实输入法交互测试。

7. 检查实现 diff，确保 `MarkdownBodyTextView` 的已确认正文提交路径中不再出现旧正文 binding 读取或全文相等比较，同时没有改动纯规则和 Store 边界。

8. 把 workflow `VERSION` 更新为 `v0.67`，同步 README、测试规范、flow、flowchart 和 update log。文档必须描述当前真实行为，不得声称已完成 Instruments 测量或人工 Mac 输入法验收。

## 测试与验收标准

### 确定性 XCTest

GitHub Actions 中必须实际执行并通过新增测试。验收必须从 `MDJournalTests.xcresult` 或 `xctest.log` 中确认新增测试名称，而不是只看总数。建议名称清楚表达契约，例如：

- `testTextViewDidChangePublishesTextWithoutReadingBinding`
- `testLineContinuationPublishesTextOnceWithoutReadingBinding`
- `testIndentationPublishesTextOnceWithoutReadingBinding`

每个测试必须证明：

- 正文 getter 次数为 `0`；
- 正文 setter 次数为 `1`；
- setter 收到的正文正确；
- 对涉及程序化选区的续写和缩进路径，UITextView 与选区 binding 的最终 range 正确；
- 现有 `MarkdownLineContinuationTests`、`MarkdownLineIndentationTests`、输入 traits 和字体测试继续通过。

这些测试证明 bridge 不再执行冗余 binding getter 和重复 setter；它们不用于证明绝对耗时、分配数量或整个 `ContentView -> JournalStore` 链路没有任何必要查找。

### 用户可见行为验收

- 普通正文输入仍即时反映到 entry，并进入现有 `JournalStore.update(_:)` 与 debounce 保存链路。
- 无序列表、待办、引用和有序列表回车续写/退出语义不变；fenced code 内仍回退系统默认输入。
- Tab / Shift-Tab、菜单和工具栏缩进语义不变。
- 外部正文更新不会在 IME marked text 期间覆盖 `UITextView`。
- 光标/选区与焦点不跳动，不发生一次操作重复发布正文。

## 风险

- UIKit delegate 契约是本优化成立的前提：普通 `textViewDidChange` 表示内容已变化，而程序化设置 `UITextView.text` 通常不会自动再次触发该 delegate。实现不得手动制造第二次回调；新增计数测试用于锁定 bridge 自身每次入口只发布一次。
- `Binding<String>` setter 的上游实现可能仍需要读取/重建 `JournalEntry` 后调用 store setter。本轮只证明并移除 Coordinator 在 setter 前的显式旧正文 getter，不应把结果夸大为整个状态链零查找或零全文复制。
- 正文直接 setter 依赖调用点只在确认变化时使用。未来若将该 helper 用于未确认值，可能重新引入无效发布；helper 命名和作用域应体现契约，且保持 `private` 或最小可见性。
- 计数测试验证调用次数和内容，不量化真实设备上的耗时或内存分配。性能收益由移除 getter 与比较的代码结构证明，后续可由人工 Instruments 采样量化。
- 本轮不运行真实 IME、键盘、first responder 或 Mac Catalyst UI；尽管守卫和状态流保持不变，仍需后续人工交互复核长文、中文输入法、回车续写和缩进体验。
