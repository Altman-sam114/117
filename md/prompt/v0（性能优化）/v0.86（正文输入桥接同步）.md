## 背景与问题证据

Mac Catalyst 或 iPad 硬件键盘进行长文输入时，UIKit 已经把正文变化写入 `UITextView`，随后 Coordinator 通过 binding 即时发布正文，SwiftUI 再调用 `updateUIView`。当前源码存在可直接确认的重复同步工作：

1. [`MDJournal/Views/MarkdownBodyTextView.swift:138-141`](../../../MDJournal/Views/MarkdownBodyTextView.swift) 的 `textViewDidChange` 直接发布当前 `UITextView` 正文和选区；普通输入会频繁触发该路径。
2. [`MarkdownBodyTextView.swift:33-55`](../../../MDJournal/Views/MarkdownBodyTextView.swift) 的 `updateUIView` 在每次 SwiftUI 更新时重新配置 bridge，然后在非 marked text 状态下比较 `textView.text != text`，即使正文刚由同一个 UIKit 控件发布，也可能再次执行长字符串比较。
3. 同一段逻辑无论选区是否变化，都会调用 [`MarkdownBodyTextView.swift:199-209`](../../../MDJournal/Views/MarkdownBodyTextView.swift) 的 `clampedRange`；`text.utf16.count` 对长正文可能产生额外的线性工作。
4. [`MDJournal/Views/EntryEditorView.swift:87-103`](../../../MDJournal/Views/EntryEditorView.swift) 在正文 binding 变化后重新评估编辑器，并从当前正文派生一次 `bodyMetrics`。v0.83/v0.84 已减少 metrics 内部的重复扫描，但没有解决 UIKit bridge 已发布正文之后的同步比较。
5. 现有 [`MDJournalTests/MarkdownTextInputConfigurationTests.swift:53-139`](../../../MDJournalTests/MarkdownTextInputConfigurationTests.swift) 已用 `BindingProbe` 锁定本地输入、回车续写和缩进的 binding 读写次数；该测试边界适合扩展同步状态语义，但当前没有锁定 `updateUIView` 的本地发布快速路径。

本轮要解决的是“UIKit 已确认发布的正文在下一次 SwiftUI bridge 更新中被重复全文比较”的风险，不预先规定必须使用某一个缓存字段、revision、布尔值或具体实现结构。Agent B 必须先阅读最新源码，选择最小且可证明正确的状态机/同步策略。

## 本轮目标

1. 在 `MarkdownBodyTextView` 中识别 UIKit 本地已发布的正文/选区状态，使后续 bridge 更新在状态仍然一致时跳过不必要的正文全文比较和选区全文长度计算。
2. 外部 binding 正文变化仍必须同步到 `UITextView`；不能因为本地快速路径而漏掉切换日记、Markdown 片段插入、外部撤销或其他 SwiftUI 来源的正文更新。
3. 保持 IME marked text、UTF-16 选区、正文即时写回、焦点请求和输入 traits 的现有行为。
4. 通过纯值状态机测试和现有 BindingProbe 测试证明本地输入、外部同步、marked text 和选区边界没有回归。
5. 只减少重复 bridge 工作，不改变正文内容、Markdown 语义、保存时序或用户数据格式。

## 实现方案与状态机要求

Agent B 不得直接照抄一个预设实现，应先确认当前代码并采用最小 diff。推荐按以下状态语义设计，具体字段名和类型可不同：

### 本地输入事件

1. `UITextView` 的普通编辑、回车续写和缩进完成后，Coordinator 已把最终正文和选区写入 binding；同时记录“本地正文/选区已发布”的同步状态或等价 token。
2. 下一次 `updateUIView` 若仍对应该本地发布结果，应跳过再次将相同正文写回 `UITextView`，并尽量跳过不必要的全文比较和选区长度 clamp。
3. 该快速路径不能阻止必要的字体、traits 或焦点同步；只能减少正文/选区同步的重复工作。

### 外部正文事件

1. 若 binding 正文来自外部来源且与 UITextView 当前本地发布状态不一致，必须进入完整正文同步路径。
2. 外部正文同步后，选区必须按现有 UTF-16 规则 clamp；`NSNotFound`、负值、越界位置和越界长度必须保持当前语义。
3. 外部正文同步不能错误地触发本地输入回调、重复写回或丢失焦点状态。

### IME / marked text

1. `textView.markedTextRange != nil` 时不得把 SwiftUI 外部正文覆盖到正在组合的 marked text 上。
2. marked text 期间的现有 `shouldChangeTextIn` 放行语义必须保持。
3. marked text 结束后，最终正文和选区仍必须正常发布并进入可验证的同步状态。

### UTF-16 选区

1. 选区仍以 `NSRange` 的 UTF-16 offset 表示；中文、emoji、组合字符和 CRLF 不能改变现有 offset 语义。
2. 当 `textView.selectedRange` 与 binding 选区已经相同且正文同步状态有效时，不应为了再次 clamp 而扫描完整正文。
3. 当选区实际变化或正文外部变化时，必须继续调用等价的 clamp 规则，不能用 `Character.count` 代替 UTF-16 长度。

### 焦点

- `synchronizeFocus` 的请求代数、最新 binding 门控、become/resign first responder 行为不得改变。
- 本地正文快速路径不能跳过焦点状态同步；焦点同步必须仍由现有 Coordinator 逻辑负责。
- 不新增真实 first responder 假设，不把焦点状态当作正文同步 token。

状态机必须至少能区分：初始/未同步、UIKit 本地发布后等待 bridge 更新、外部正文待同步、marked text 暂停同步、正文已同步且选区已同步。若现有 UIKit 生命周期无法安全区分某状态，Agent B 应保持保守同步并记录原因，不得为追求跳过比较而牺牲外部更新或 IME 正确性。

## 纯值与 Binding 测试设计

测试必须留在 `MarkdownTextInputConfigurationTests.swift`，不创建 SwiftUI host，不启动 App，不使用截图或真实键盘。可新增 internal 纯值 `MarkdownBodyTextView` 同步策略，也可通过 Coordinator 的可测方法测试状态转移；不得为了测试把生产状态暴露为持久化 API。

至少覆盖：

1. 初始状态：未确认本地发布时，外部正文变化需要同步；初始选区按 UTF-16 clamp。
2. 本地输入：Coordinator 发布正文后，下一次等价 bridge 更新不重复替换正文；BindingProbe 不新增旧正文 getter，正文 setter 次数保持当前契约。
3. 外部更新：外部正文变更必须重新同步，即使它与上一次正文长度相同；更新后选区按现有 clamp 规则处理。
4. marked text：marked text 状态下不覆盖 UITextView 内容；结束后可以接受最新外部状态或本地发布状态。
5. 选区：相同选区走快速路径；`NSNotFound`、越界位置、越界长度、中文/emoji/组合字符正文继续得到正确 UTF-16 结果。
6. 焦点：现有 `synchronizeFocus` 的 generation 门控测试和行为不被改变；若本轮没有新增焦点测试，必须说明代码 diff 未改变该方法。
7. 回车续写和缩进：保留现有测试，确认新增同步状态没有引入二次正文发布或旧正文读取。

测试可以证明状态转移、值语义和 binding 读写行为，但不能证明真实 Mac Catalyst 的每秒分配、键盘延迟、IME 服务实现或 SwiftUI frame 性能。Agent B 和 Agent C 必须把这些限制写入报告/文档，不能写成已完成的 Instruments 验证。
