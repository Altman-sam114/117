## 2. 版本与目标

版本：v0.75。

目标：降低 Mac Catalyst 宽屏长文写作时“每次正文变化都在主线程同步整篇 Markdown 解析并重建预览”的输入延迟，建立可证明的 trailing debounce 与 latest-wins 更新边界。

本轮必须满足：

1. 正文编辑 binding 和 JournalStore 内存状态继续即时更新。不能为了预览性能延迟正文、光标/选区、分类/心情或标题写回。
2. 预览首次出现时立即使用当前正文生成可见内容，不能让空白预览等待首个 debounce。
3. 正文连续变化时采用固定 trailing 延迟。等待期间保留上一份已经显示的解析结果，不在每个字符到达时同步调用 MarkdownBlockParser.parseDocument。
4. 多个未完成请求必须 latest-wins：只允许最新正文版本发布到预览，旧 request 即使迟到也不能覆盖新结果。
5. 切换日记、预览离开视图、窄屏编辑/预览模式切换或预览列隐藏时，旧请求必须取消或失效；旧日记正文不能回写到新日记预览。
6. 只因 accent、容器宽度、Dynamic Type 或窗口重排变化时，不得重新解析未改变的 Markdown；这些变化可以重新布局已有解析数据。
7. 预览仍使用现有 MarkdownBlockParser 语义、section grouping、inline Markdown、颜色、内容顺序、横向代码滚动和空状态。

推荐延迟由可测试的 internal contract 集中维护，例如 150ms。实现可以使用现有 JournalSaveScheduling 风格的手动 scheduler，或同等可注入的取消/触发边界。不得用固定 sleep、轮询、GCD 或 wall-clock 猜测来测试时序。

## 3. 问题证据

当前 MarkdownPreviewView.body 直接调用 MarkdownBlockParser.parseDocument(markdown)。EntryEditorView 宽屏默认同时构造预览，正文每次 binding 变化都会使预览输入变化。解析器会生成 blocks 和 section groups，这是整篇正文的 O(N) 派生。

v0.73 只把 JSON encode/atomic write 移出主线程，并改善保存 debounce 的等待快照；没有延迟或合并 UI 预览派生。v0.74 只改善编辑器头部 Dynamic Type 布局；没有改变预览解析成本。本轮必须针对真实生产路径实现行为，不得只新增一个生产 view 不消费的测试策略。

## 5. 架构与行为契约

### 5.1 预览状态

预览视图应持有已解析的值状态或等价的明确 render state；body 不应在每次 SwiftUI 重算时重新调用 parser。可以保留现有 MarkdownPreviewView(markdown:accent:maxContentWidth:) 调用兼容性，也可以用最小参数扩展传递稳定 entry identity，但生产 view 必须消费实际调度结果。

至少区分：

- markdown：只有它改变时才产生新的 parse request。
- 稳定 entry identity：切换 entry 时令旧 request 失效，即使两篇正文相同也不能让旧 token 回写。
- isPreviewVisible 或 view task 生命周期：隐藏/离开时取消等待和在途发布。
- accent、最大内容宽度、Dynamic Type：只影响已有 parse result 的渲染布局，不成为 parse request key。

首次展示应立即获得当前正文的 parse result；后续正文变更才进入 trailing debounce。等待期间显示上一份 result，可以有轻量更新中状态，但不得加入宣传性说明或固定高度。

### 5.2 latest-wins 与取消

实现必须有明确的 generation/request token 或同等单调身份：

1. 接受新正文快照时递增 token，并取消旧的可取消任务。
2. scheduler 触发后，在发布结果前再次确认 token、entry identity 和 view 仍有效。
3. 旧 parse 即使完成，也只能丢弃，不能通过晚到 completion 覆盖新结果。
4. 切换 entry、销毁预览 view 或隐藏预览时让旧 token 失效；不能依赖 SwiftUI 恰好重建 view 作为唯一保护。
5. 相同正文的重复 update 不增加 request generation；焦点、选区、颜色、窗口尺寸不能触发 parser。

如果将纯解析移到非 MainActor，返回值必须满足严格 Swift concurrency 的 Sendable/隔离要求，不能用 Task.detached 绕过隔离。若仍在 MainActor，必须先用 trailing debounce 减少触发次数；不要引入数据竞争或改变 Markdown 结果。

### 5.3 与保存链路隔离

预览 debounce 与 JournalStore 保存 debounce 是两条独立链路：

- 预览使用当前正文快照，仅服务显示。
- Store 仍即时接收正文 binding，并按既有 revision/scheduler 保存。
- flushPendingSave 不等待预览 parse；预览取消也不取消已提交持久化请求。
- 不把 parsed document 写入 JournalEntry 或 JSON。

## 6. 测试要求

优先新增纯值/确定性测试，必须锁定视图真正消费的策略，不要建立生产代码不调用的假 contract。可扩展既有测试文件，也可新增专用测试文件。

至少覆盖：

1. 首次预览：当前正文立即生成初始结果。
2. trailing：新正文进入后，scheduler 未触发前不发布新结果；触发后发布最新快照。
3. 连续输入：A、B、C 连续到达只发布 C；A/B 的取消或迟到结果不能覆盖 C。
4. same-content：正文未改变时不增加 generation；仅焦点、选区、accent、宽度或字号变化不请求 parse。
5. entry switch：旧 entry 的 pending/迟到结果不能发布到新 entry；新 entry 能显示自己的正文。
6. visibility cancellation：隐藏或销毁预览后不启动新的 parse，也不发布失效结果。
7. 保留现有所有 Markdown parser/preview 语义测试；不能用策略测试替代解析边界。

可以增加不设 wall-clock 通过阈值的 XCTest.measure 观察数据，但不能把 CI 机器耗时作为 gate。测试不能使用真实 Task.sleep、usleep、轮询、semaphore、GCD、detached task 或固定延迟猜测。

云端 artifact 中必须明确看到新增策略测试实际执行且通过；既有 v0.74 的 185 项不能被删除或 skipped，v0.75 实际总数以最新 MDJournalTests.xcresult / xctest.log 为准。
