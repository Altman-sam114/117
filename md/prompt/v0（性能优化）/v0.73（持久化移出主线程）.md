## 背景与现状证据

当前 `JournalStore` 整体标记为 `@MainActor`，链路为：

```text
正文 Binding -> JournalStore.update(_:) -> 内存 entries 即时更新
  -> 450ms MainActor debounce
  -> MainActor JSONEncoder.encode(entries)
  -> MainActor Data.write(.atomic)
```

当前行为边界：

- `update(_:)` 取消旧 debounce 并安排 450ms 后保存，内存值立即可见。
- `createEntry()` 和 `delete(_:)` 取消 pending debounce 后同步调用 `save()`；现有测试因此在同步 API 返回后立即读取磁盘。
- `flushPendingSave()` 是同步 API，仅当存在 pending debounce 时取消延迟并同步保存；若 debounced write 已经开始，它没有可等待的独立写入完成边界。
- `save()` 每次新建 `JSONEncoder`，使用 `.iso8601` 日期、`[.prettyPrinted, .sortedKeys]` 输出和 `Data.write(..., options: [.atomic])`。
- 写入失败直接设置 `errorMessage`；没有 revision，因此旧请求失败可能在并发迁移后污染较新状态。
- 首次无文件时 `load()` 创建 starter entry 后同步保存；读取和 decode 当前也在 MainActor，但本轮性能目标只要求把所有 encode/write 移出 MainActor，读取迁移不是本轮目标。
- `ContentView` 在 `scenePhase != .active` 时同步调用 `flushPendingSave()`。

## 本轮目标

1. 新建独立生产文件 `MDJournal/Stores/JournalPersistenceWriter.swift`，定义持久化跨隔离域契约和单写者 actor；必须登记到现有显式 Xcode project 的 Stores group 与 app target Sources build phase。
2. `JournalEntry`、`JournalEntry.Category`、`JournalEntry.Mood` 显式声明 `Sendable`，使不可变 `[JournalEntry]` 快照可合法跨 actor；不得使用 `@unchecked Sendable`。
3. 定义 internal 且 `Sendable` 的 snapshot、result、writer protocol。snapshot 至少包含单调 `revision` 和完整 entries 值；result 必须区分真实写入成功、同 revision 已成功的幂等结果、旧 revision 被拒绝、写入失败及其 revision/可展示字符串。
4. 使用 actor 作为唯一 JSON writer。actor 内维护 `highestAcceptedRevision` 和 `durableRevision`：拒绝小于最高已接受 revision 的旧请求；相同 revision 已成功时不重复写；相同 revision 上次失败时允许重试；较新 revision 失败后禁止旧 revision 回退覆盖文件。
5. actor 的 encode + write 临界区内禁止出现任何 `await` 或其他挂起点，确保一次写入不可重入。不得在 actor 外预编码，也不得使用 `DispatchQueue.sync`、semaphore、锁等待 MainActor 或 `Task.detached()`。
6. 保持 JSON 策略逐项不变：`JSONEncoder.dateEncodingStrategy = .iso8601`、`outputFormatting = [.prettyPrinted, .sortedKeys]`、`Data.write(..., options: [.atomic])`。不得改变字段、文件名、兼容解码、排序或持久化格式。
7. `JournalStore` 继续是 `@MainActor ObservableObject` 和唯一集合修改入口。每次有效 mutation 严格递增 revision：create 总是有效；update 只在 ID 存在并真实进入当前更新链路时递增；delete 只在确实删除目标时递增。无效 ID 调用不得制造 revision 或无意义写入。
8. `update(_:)` 继续内存即时更新并按当前 450ms 默认值 debounce；延迟结束后只提交该 revision 的不可变快照给 actor，MainActor 不执行 encode 或磁盘 I/O。
9. `createEntry()` / `delete(_:)` 必须取消尚未触发的 debounce 并绕过 450ms 延迟，立即提交当前 revision 快照。同步 API 保留内存和 selection 立即变化，但不得继续声称“方法返回时磁盘已经完成写入”；需要磁盘完成保证的调用者必须 `await flushPendingSave()`。
10. 首次无存储文件时 starter entry 的 encode/write 也必须走同一个 actor，不能保留 MainActor `save()` 旁路。已有文件的同步读取/解码可保持现状。
11. 将 `flushPendingSave()` 改为 async 完成屏障：取消尚未触发的 debounce，提交并等待当前快照；等待期间若 MainActor revision 又变化，必须继续循环到最新 revision，且最新 revision 不再等待 debounce。只有当返回时观察到的 revision 已完成一次成功、幂等或明确失败尝试，flush 才能返回。
12. flush 的失败必须通过可测试 result 明确返回，并按最新 revision 更新现有保存错误 UI；失败不能错误地推进 durable revision，后续 flush 必须能用相同 revision 重试。
13. `ContentView` 的 scene phase 路径使用普通 `Task { await store.flushPendingSave() }`，不得同步阻塞 UI，不得使用 GCD、semaphore 或 detached task。保持现有 `phase != .active` 触发条件。
14. 所有异步 result 回到 Store 后必须按 revision 仲裁：旧 success、旧 failure、旧 rejected result 都不得改变当前错误或 durable 状态。较新成功可清理对应的旧“写入失败”提示，但不得清理“读取本地日记失败”或人工无关错误；需要内部错误来源或等价状态，不能只比较任意本地化字符串。
15. debounce Task 的生命周期必须明确区分“尚在等待”与“已经提交给 writer”。新 mutation 可取消旧的等待任务；一旦快照已经提交 actor，不得因替换 debounce、scene flush 或 `JournalStore.deinit` 取消该写入。Task closure 不得与 Store 形成强引用环。
16. `deinit` 不得尝试异步 flush，也不得取消 actor 已接受或立即提交的写入。若选择取消尚未提交的 debounce，必须记录它只能依赖 scene phase flush 保障正常生命周期；不得把 deinit 或异步 scene flush 描述为进程强杀下的绝对 durability。
17. 为 writer 和 debounce scheduler 提供 internal、Sendable、可注入的测试边界。测试 gate 必须由 actor/continuation 显式开启和释放，不得依赖固定 sleep、轮询时长、Dispatch semaphore 或真实磁盘变慢来猜测时序。
18. 同步 workflow 为 v0.73、测试基线、README、核心流程、流程图和更新日志，并由 GitHub Actions 完整重验证 generic iOS build、Mac Catalyst build 与 XCTest。

## 架构与并发契约

### 1. Sendable 快照和结果

生产文件中应采用语义等价的 internal 契约：

```swift
struct JournalPersistenceSnapshot: Sendable {
    let revision: UInt64
    let entries: [JournalEntry]
}

enum JournalPersistenceResult: Sendable, Equatable {
    case written(revision: UInt64)
    case alreadyDurable(revision: UInt64)
    case rejectedStale(revision: UInt64, highestAcceptedRevision: UInt64)
    case failed(revision: UInt64, message: String)
}

protocol JournalPersistenceWriting: Sendable {
    func persist(_ snapshot: JournalPersistenceSnapshot) async -> JournalPersistenceResult
}
```

允许调整命名，但必须保留上述可测试语义。生产 writer、Store 和测试 fake 必须使用同一 protocol，不得另写只为测试存在但生产不消费的平行契约。

`JournalEntry` 及嵌套枚举显式增加 `Sendable`：

```swift
struct JournalEntry: Identifiable, Codable, Hashable, Sendable
enum Category: String, CaseIterable, Codable, Identifiable, Sendable
enum Mood: String, CaseIterable, Codable, Identifiable, Sendable
```

所有存储属性均为可安全跨隔离域的值类型；禁止用 `@unchecked Sendable` 绕过诊断。

### 2. 单写者 actor revision 规则

`JSONJournalPersistenceWriter` 必须是 actor，并且 actor 的 production `persist` 方法在读取/更新 revision、encode 和 atomic write 之间没有 `await`。逻辑顺序必须等价于：

```text
收到 revision r
  -> r < highestAccepted：拒绝，不写盘
  -> r >= highestAccepted：highestAccepted = r
  -> durableRevision == r：返回 alreadyDurable，不重复写
  -> encode + atomic write 成功：durableRevision = r，返回 written
  -> 失败：durableRevision 不变，返回 failed；r == highestAccepted 可重试
```

关键不变量：

- `highestAcceptedRevision` 单调不减。
- `durableRevision` 只在成功写入后推进，且不得倒退。
- 较新 revision 即使失败，也已经阻止更旧请求随后覆盖磁盘。
- 同 revision 成功后重复请求幂等；同 revision 失败后重复请求必须真正重试。
- actor 是唯一 encode/write 执行者；Store 中不得残留同步 `save()` 或其他 Data.write 旁路。

### 3. Store revision 与提交

`JournalStore` 保持 `@MainActor`，持有 writer、scheduler、当前 revision、Store 已确认的 durable revision、pending debounce 及错误来源状态。建议将“递增 revision + 捕获 entries 值快照”收敛到一个小方法，防止不同 mutation 漏增或复用 revision。

提交 Task 必须：

- 强持有 immutable snapshot、writer 和 scheduler 所需值。
- 只弱持有 Store 用于结果回传，避免 `Store -> Task -> Store` 环。
- 等待 debounce 时可被后续 mutation 取消。
- 在真正调用 writer 前清楚标识 pending 已触发；已经进入 writer 的任务不再作为可取消 debounce 处理。
- writer 返回后切回 MainActor，只有 result revision 仍与当前状态相关时才更新 durable/error 状态。

### 4. async flush 线性化

`flushPendingSave()` 应是 `@discardableResult async` API，返回最终 `JournalPersistenceResult?` 或语义等价的明确结果。算法必须等价于：

```text
取消当前尚未触发的 debounce
loop:
  在 MainActor 捕获 currentRevision + entries snapshot
  await writer.persist(snapshot)
  按 revision 仲裁 result
  如果 currentRevision 仍等于捕获 revision：返回本次明确结果
  否则取消新产生的 debounce，继续写当前最新 revision
```

不允许只等待进入 flush 前已经存在的 Task handle，因为 flush 等待时 create/update/delete 仍可在 MainActor 发生。也不允许失败后在同一次 flush 中无限自动重试；最新 revision 的一次失败应明确返回并展示，后续人工/生命周期 flush 再以同 revision 重试。

### 5. 错误来源与仲裁

需要区分读取错误与 revision 绑定的写入错误，允许采用 private enum/struct 或等价设计：

- 读取失败不绑定写 revision，后续 writer 成功不得把它清掉。
- 写入失败只有 `failed.revision == currentRevision` 时能展示。
- 更新后迟到的旧失败不得展示；旧成功也不得清除当前较新失败。
- 同 revision 或较新 revision 成功后，可清除当前仍对应旧写入错误的提示和来源标记。
- 用户关闭 alert 后状态必须一致；若引入 `dismissError()`，同步调整 `ContentView` 两个清理入口，避免 public setter 绕过来源状态。

### 6. 生命周期与 durability 边界

- `ContentView` 在 `scenePhase != .active` 时启动普通 Task 并 await flush；UI 不同步等待磁盘。
- `deinit` 不能 await，禁止在其中创建未经跟踪的“最后一次 flush”并宣称可靠。
- 已提交 writer 的请求由 actor 串行完成，不应因 Store deinit 或 debounce handle 取消而被主动取消。
- pending debounce 是否在 Store deinit 后继续由实现选择，但必须无 retain cycle、测试 cleanup 无竞态，并在文档中准确写出语义。
- 未引入 background execution lease，因此系统在异步 scene flush 完成前快速挂起、崩溃或强杀仍可能丢失最近尚未 durable 的内存更新。这是明确残余风险，不得写成“绝不丢数据”或“保证落盘”。

## 关键时序验收

实现和测试必须逐项证明：

1. **debounced write 已开始后 update**：旧写可能先完成，但新 revision 最终后写；旧结果和错误不得污染新 revision。
2. **debounced write 已开始后 create/delete**：create/delete 立即改变内存并绕过 debounce 提交新快照；旧请求先完成或后到达都不得覆盖新快照。
3. **debounced write 已开始后 flush**：flush 必须等待 writer，并在返回前覆盖调用期间出现的最新 revision。
4. **flush 等待期间 update/create/delete**：MainActor 仍可执行 mutation；flush 检测 revision 变化后继续写最新快照。
5. **较新请求先到、旧请求后到**：actor 明确返回 rejected stale，磁盘保持较新内容。
6. **同 revision 成功后重复提交**：返回幂等结果，不做第二次 encode/write。
7. **同 revision 失败后再次 flush**：允许重试；成功后 durable revision 推进并合理清理对应写错误。
8. **deinit**：不形成 Task retain cycle，不取消已经提交的 writer 工作，不虚构进程终止 durability。

## 确定性测试要求

测试不得使用 `Task.sleep` 固定等待、轮询文件直到变化、依赖机器速度、Dispatch semaphore、`Task.detached()` 或真实大文件制造阻塞。使用 internal writer/scheduler 注入、actor gate 与 checked continuation 明确控制“延迟已开始”“writer 已收到”“允许完成”等阶段；continuation 必须只 resume 一次，测试结束不得遗留等待任务。

建议将当前 5 项 `JournalStoreTests` 重构/扩展为约 14 项，至少覆盖：

1. **JSON 字节策略不变**：固定 entries 经 production writer 写出的 Data 与使用 `.iso8601 + prettyPrinted + sortedKeys` 的参考 encoder 字节完全一致，并能按现有 decoder 解码。
2. **乱序 revision**：先接受较新 revision，再提交较旧 revision；旧请求返回 rejected stale，文件不回退。
3. **同 revision 成功幂等**：第二次提交返回 already durable，并通过结果/可注入计数证明没有第二次写入。
4. **失败允许同 revision 重试**：第一次确定性失败不推进 durable，修复 writer 条件后相同 revision 成功；更旧 revision 始终不能趁失败回写。
5. **持久化等待不阻塞 MainActor**：gate writer 挂起期间，另一个 `@MainActor` 操作能确定性执行；释放 gate 后写入完成。该测试不得把“fake actor 可挂起”冒充 production actor 内有 await，production 源码仍须审查无挂起点。
6. **update debounce 由手动 scheduler 控制**：update 后内存立即最新；scheduler 未释放前 writer 未收到；释放后只收到最后一个 revision/快照。连续 update 取消旧等待，不依赖 120/220ms 猜测。
7. **flush 明确等待**：scheduler 未释放时调用 flush，flush 直接取消等待并提交；writer gate 未释放前 flush 不返回，释放后返回准确 result。
8. **flush 追赶调用期间最新 revision**：flush 等待旧 revision 时执行新的 update/create 或 delete；MainActor mutation 成功，flush 在旧结果后继续提交最新 revision，最终返回最新 result。
9. **create 内存即时 + flush 磁盘**：同步 create 返回后立刻能从 Store 取到新条目；不再立即断言磁盘已写。await flush 后磁盘包含该 ID。
10. **delete 内存即时 + flush 磁盘**：同步 delete 后 Store 立即移除；await flush 后磁盘也移除。无效目标不递增 revision、不提交 writer。
11. **旧失败错误仲裁**：旧 revision 被 gate 后产生 failure，此时 Store 已有较新 revision；旧错误不显示、不覆盖较新状态。
12. **最新失败、重试与错误来源**：最新失败显示现有中文保存错误并明确返回 failure；后续 flush 用相同 revision 重试成功并清理对应写错误；读取错误不得被 writer success 清除。
13. **正文更新保持排序**：保留现有 createdAt 未变时数组顺序不重排的测试。
14. **日期更新按需排序**：保留现有 createdAt 变化时重新排序的测试。

- MainActor 上不再执行任何 JournalEntry JSON encode 或 Data atomic write；所有保存入口统一进入 production actor。

## 风险与停止条件

残余风险必须如实保留：

- 全量 JSON encode/write 虽移出 MainActor，单次成本仍是全部 entries 的 `O(T)`，本轮没有改为增量存储。
- `[JournalEntry]` 快照会复制 Array 值并持有全部 String storage；Swift copy-on-write 避免立即深拷贝，但后续 mutation 可能产生额外分配。
- create/delete 同步 API 返回时磁盘可能仍在写；只有 awaited flush/result 提供进程存活期间的明确完成边界。
- scene phase Task 不持有系统 background execution lease；系统快速挂起、崩溃、断电或强杀仍可能使最新内存 revision 未 durable。
- actor 串行化避免旧快照最终覆盖，但底层文件系统、磁盘空间、权限和原子替换失败仍会产生用户可见错误。
- XCTest gate/scheduler 证明状态机和 MainActor 可继续调度，不等价于 Instruments 卡顿数据、真实大数据性能、后台挂起实验或 Mac 长时间写作体验。

必须停止或退回的条件：

- 无法在不改变 JSON 字节策略的情况下完成 actor 迁移。
- 需要提高 deployment target、Swift language mode、增加依赖或使用 unchecked Sendable 才能编译。
- 无法证明旧 revision 不覆盖新 revision，或 actor 临界区需要 await。
- flush 无法明确等待最新 revision，失败无法重试，或读取/写入错误来源无法可靠区分。
- gate/scheduler 测试仍依赖固定延迟、semaphore、detached task 或存在 continuation 泄漏。
- project 文件有重复/缺失登记、工作区有无法判断归属的冲突、CI 连续同因失败，或缺少远端/artifact 权限。
