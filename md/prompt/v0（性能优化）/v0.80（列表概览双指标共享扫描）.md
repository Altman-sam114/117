## 背景

JournalListOverviewSnapshot 当前对每篇日记正文分别调用：

1. JournalEntryBodyMetrics.wordCount(in:)；
2. JournalSection.containsLevelThreeSection(in:)。

两个入口都对整篇正文做线性扫描，列表概览在日记数量或正文长度增加时产生重复扫描。JournalEntry.swift 的 v0.78 已将 JournalEntryBodyMetrics 内部的词数和完整小节派生合并为一次扫描，但本轮目标不同：列表概览只需要两个轻量字段，不能为了复用 JournalEntryBodyMetrics(body:) 而构造完整 [JournalSection]。

## 目标

1. 新增非持久化、内部可用的 JournalEntryOverviewMetrics，或等价的模型层内部结果类型，至少包含：
   - wordCount: Int
   - hasLevelThreeSection: Bool
2. 让 JournalListOverviewSnapshot 对每篇正文只消费一次共享线性扫描结果。
3. 共享扫描不得构造完整 sections、section markdown、section excerpt 或正文 summary。
4. 保持 JournalListOverviewSnapshot 的 totalWords、entriesWithSections、sectionCoverage、本周词数、分类词数、洞察文案和所有 UI 表现完全不变。
5. 保留既有 JournalEntryBodyMetrics.wordCount(in:)、JournalSection.containsLevelThreeSection(in:)、JournalSection.extract(from:) 的调用契约和结果语义。
6. 将实现限制在模型/列表概览边界，不把正文解析逻辑搬入 SwiftUI View 或 JournalStore。

## 架构依据

- JournalEntry 是正文模型和兼容派生边界；非持久化 overview metrics 应放在 MDJournal/Models/JournalEntry.swift。
- JournalBodyDerivation 是 v0.78 已有的私有模型层扫描边界。优先扩展其内部结果/扫描选项，令同一条逐字符路径同时计算旧词数和轻量 marker 布尔值；也可新增同文件内的等价私有扫描器，但不得复制一个会再次完整扫描正文的调用链。
- JournalListOverviewSnapshot 是唯一需要接入新 metrics 的生产调用方；每个 entry.body 在该循环内只能触发一次 overview 派生。
- 新结果类型只保留两个字段，不能包含 sections 属性。扫描实现必须在 derivesSections == false 的路径上跳过 JournalSectionAccumulator 的完整内容构造。
- JournalEntry 的持久化仍只由已有存储属性和 CodingKeys 决定；新增计算/内部 metrics 不得进入 JSON。

## newline / marker / fenced-code 兼容边界

新 hasLevelThreeSection 必须与既有 JournalSection.containsLevelThreeSection(in:) 逐输入一致，而不是只与常见 LF 示例一致。

必须保留以下语义：

- LF、CR、CRLF、VT、FF、NEL (U+0085)、LINE SEPARATOR (U+2028) 和 PARAGRAPH SEPARATOR (U+2029) 都是有效行边界；CRLF 不得漏掉其后的 marker，也不得把 marker 误判为行内内容。
- 每行只能跳过连续 ASCII 空格 U+0020 和 tab U+0009；NBSP、全角空格、BOM 等非 ASCII 空白不能作为合法 marker 前导。
- marker 必须精确从行首（允许上述 ASCII 前导后）开始为 ### + 空格；### 无分隔、### 后接 tab、#### + 空格、行内 正文 ### 标题 均不得命中。
- ### + 空格、### + 两个空格 + 标题、仅空标题、EOF marker、连续 marker 和尾随换行仍表示存在小节；本轮只返回布尔值，不需要生成标题或正文。
- fenced code 不建立状态机。围栏内行首的 ### + 空格 仍按普通合法 marker 处理，这是当前兼容 API 的既有行为；不得引入 Markdown parser 的 fenced-code 规则。
- 词数必须继续遵守现有 JournalEntryBodyMetrics.wordCount(in:) 的逐 Character 语义，包含 emoji、组合字符、Unicode 空白和尾随换行边界。不能用新的 split 或近似分词规则替换它。

实现 marker 检测时，优先在同一正文遍历中按 Unicode scalar 顺序维护行首/ASCII 前导/### + 空格匹配状态，同时继续沿用现有词数的 Character 语义。不要在计算词数后再调用 containsLevelThreeSection，也不要用第二个 components(separatedBy:) 或 split 扫描正文。对 CRLF、newline 附近组合字符等边界，必须以既有兼容 API 的结果为 oracle。

## 最小 characterization 测试

在 JournalEntryTests 增加一个确定性测试方法，使用一组表格输入，逐项断言：

~~~swift
let overview = JournalEntryOverviewMetrics(body: testCase.body)
XCTAssertEqual(overview.wordCount, JournalEntryBodyMetrics.wordCount(in: testCase.body))
XCTAssertEqual(
    overview.hasLevelThreeSection,
    JournalSection.containsLevelThreeSection(in: testCase.body)
)
~~~

最小表格必须包含：

- 空正文、纯空白和只有 newline 的正文。
- 普通正文、emoji、组合字符、Unicode 空白和尾随换行。
- LF、CR、CRLF 以及 VT/FF/NEL/LS/PS 混合 newline。
- 文档开头、正文后、EOF、连续 marker、空标题、多个合法标题。
- ASCII 空格/tab 前导、非 ASCII 空白前导、### 无空格、### 后接 tab、#### + 空格和行内 marker。
- fenced code 内的合法 ### + 空格 marker，确认其仍命中。
- 至少一个长正文无小节和一个长正文末尾有小节，用于确认结果不会因扫描到 EOF 失真，但不做耗时断言。
